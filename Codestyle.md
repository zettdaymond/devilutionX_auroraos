Заголовочные файлы

Файлы заголовков должны быть автономными - то есть компиляция cpp файла, в который включен этот заголовок, не должна зависеть от того, после какого заголовка включен этот файл. Пользователи не должны соблюдать особые условия для включения заголовка.

Файлы, предназначенные для включения в заголовок (в середину или в конец) должны заканчиваться на .inc и использоваться с осторожностью. 

Реализация шаблонов (или методов класса, если это нужно по какой то причине) должна быть непосредственно в заголовке, использовать для этого файлы .inc - нельзя.

Каждый заголовок должен иметь защиту от повторного включения - #pragma once
Forward declarations и политика include'ов

Мы используем Forward declarations, чтобы уменьшить время компиляции. Но тем не менее, мы делаем #include на зависимости, которые нужны клиенту потом для работы, например:
#include <typeinfo>
 
#include <common/TypeAliases.h>
 
class RenderNode;
 
class Node {
public:
    //Типы SPtr и Component - часть возвращаемого значения, включаем заголовок
    //std::type_index - передается по значению, включаем заголовок.
    auto FindComponent(std::type_indextype_index) -> SPtr<Component>;
 
    // SPtr - шаблон, включаем заголовок
    // RenderNode - указатель, пишем forward
    bool IsRenderNode(SPtr<RenderNode> const& rn);
}

Включаем заголовки в следующем порядке:

    Связанный заголовок с cpp файлом

    Заголовки других библиотек из нашего проекта
    Заголовки thirdparty-библиотек
    Заголовки стандартной библиотеки C++
    Заголовки системы

Каждая секция заголовков должна быть сгруппирована

Заголовки, со 2 по 5 пункт влючительно инклубятся через < >

Заголовки для 1 и 6 пункта инклудятся через " "

1.3. Именование типов

Типы именуются UpperCamelCase'ом. В имени типа допускается использование аббревиатуры, если это аббревиатура от названия - флеймворка, апи итд. Допустимо сохранить оригинальный стиль именования аббревиатуры.

В именах не используем сокращения, однобуквенные маркеры чего-либо, например Class == C → CPoint, CList и прочее.

Имена всех типов — классов, структур, псевдонимов типов, перечислений и параметров шаблона типа — имеют одинаковое соглашение об именах. Имена типов должны начинаться с заглавной буквы и содержать заглавную букву для каждого нового слова. Никаких подчеркиваний.

Пример: CommandBufferGLES, OrthoCameraProjection, RenderPass.
class CommandBufferGLES {};
struct OrthoCameraProjection{};
enum class Rotation{};using RotationAlias = Rotation;
1.4. Именование переменных
1.4.1. Общие правила

Всем переменным (включая параметры функций) даются имена lowerCamelCase'ом.
std::string appName = "VESDK"; // Правильно
std::string app_name = "VESDK"; // Неправильно
1.4.2. Именование полей класса

Поля класса (статические и нестатические) именуются по тому же правилу, что и обычные переменные, но с добавлением m_  перед именем переменной:

Правильно
class YobaClass {
private:
    static int m_yobaStaticVar;
    int m_yobaVar;
}

Неправильно
class YobaClass {
private:
    static int yoba_static_var_;
    int yoba_var;
}
1.4.3. Именование полей структуры

Поля структуры (статические и нестатические) именуются по тому же правилу, что и обычные переменные

Привильно:
struct YobaStruct {
    static int yobaStaticVar;
    int yobaVar;
}

Неправильно:
struct YobaStruct {
    static int m_yobaStaticVar;
    int yoba_var;
}
1.5. Именование констант

Переменные, объявленные как constexpr или const и значение которых зафиксировано на протяжении всей программы, именуются с начальной буквой «k», за которой следует UpperCamelCase. Символы подчеркивания можно использовать в качестве разделителя в тех редких случаях, когда для разделения нельзя использовать заглавные буквы.

Пример:
constexpr auto kMicrosecondsInASecond = 1'000'000u;

Не следует использовать такие имена для констант, значение которых может меняться на протяжении работы программы, в этом случае используем соглашение об именовании переменных:

Неправильно:
std::string GetDescription(int userID) {
    // Неправильно: GetUserBasePath - может вернуть разные значения для своего аргумента
    const auto kMillisecondsInASecond = GetUserBasePath(userID);
}
1.6. Именование функций и методов

Всем функциям и методам задаются имена в UpperCamelCase
std::filesystem::path GetDescriptionPath(int userID) {
    constexpr static auto kDescriptionDirName = "description";
 
    return GetUserBasePath(userID) / kDescriptionDirName;
}

1.8. Именование перечислений

Перечисления (как с областью видимости, так и без) нужно называть как константы, но не как макросы - то есть использовать EnumEntry, а не ENUM_ENTRY.

Хорошо:
enum class RenderError {
    OutOfMemory = 0,
    //...
}

Плохо:
enum class RenderError {
    OUT_OF_MEMORY = 0,
    //...
}
1.9. Именование макросов

Прежде всего нужно себя спросить, а точно ли я хочу использовать тут макрос? Может быть я могу сделать все что мне нужно используя константу, или constexpr функцию?

Если есть возможность написать код без макроса, то пишем код без макроса. Исключение - только если без него не никак не обойтись (используем возможности макросов, которых нет в языке)

Макросы именуются капсом - THIS_IS_MY_SUPER_MACROS
#define THIS_IS_MY_SUPER_MACROS(x) ...

Порядок объявления

Группируем похожие объявления вместе - не должно быть 5 public, 2 private итд

Размещаем сначала public секцию, потом protected, потом private.

Пропускаем секции, которые будут пустые.

В каждом разделе стараемся группировать похожие типы объявлений и использовать следующий порядок:

    Типы и псевдонимы типов (typedef, using, enum, вложенные структуры и классы, а также дружественные типы)
    Статические константы
    Статические  методы, включая фабричные методы
    Конструкторы и операторы присваивания
    Деструктор
    Перегруженные виртуальные методы
    Все остальные методы (а также дружественные функции)
    Статические поля класса
    Нестатические поля класса 

Не вставляйте большие определения методов в определение класса. Обычно в строке могут быть определены только критичные к производительности и очень короткие методы. 

Пример:
class EffectMaterial : public Material
{
public:
    struct SampledTexture {
        //...
    };
 
    struct UniformValue {
        //...
    };
 
    using Uniforms = std::map<std::string,  UniformValue >;
 
    static auto MakeEffectMaterial() -> SPtr< EffectMaterial >;
 
    EffectMaterial() = default;
    EffectMaterial( const Effect& e );

    auto GetVertexSource() -> std::string_view const override;

Когда кто - struct vs class

Используем структуру только для пассивных объектов, хранящих данные, для всего остального - класс.

Ключевые слова struct и class ведут себя в C++ почти одинаково, однако мы добавляем к каждому ключевому слову собственное семантическое значение. Структуры следует использовать сгруппированного набор данных - пассивных объектов, но структура не должна иметь инварианты, предполагающие отношения между различными полями, поскольку прямой доступ пользователя к этим полям может нарушить эти инварианты. 

Все поля структуры должны быть общедоступными.

В структуре могут присутствовать конструкторы, деструкторы и вспомогательные методы.

Иными словами, структура - сгруппированный набор данных, класс - это что то сложное с кучей состояний.

Пример:
struct BufferDesc
{
    constexpr BufferDesc& SetPurpose( BufferPurpose const& p ) noexcept {
        purpose = p;
        return *this;
    }
 
    constexpr BufferDesc& SetReadOnly( bool ro ) noexcept {
        is_read_only = ro;
        return *this;
    }
 
    constexpr BufferDesc& SetSizeBytes( uint32_t bytes ) noexcept {
        size_bytes = bytes;
        return *this;
    }
 
    BufferPurpose purpose;
    bool is_read_only = false;
    uint32_t size_bytes;
};
Доступ к данным класса

Все поля класса должны быть приватными, публичными разрешено быть только константам.

В случае, когда нужно получить или установить значение полю класса - пишем Getter/Setter. Да, это потребует написать какое то количество boilerplate кода, но зато мы всегда сможем встать дебагером на изменение пепременной, добавить в метод логи итд.

Стоит заметить, что Getter/Setter - должны быть быстрыми операциями, возвращабщие валидные значения. Когда предполагается продолжительные операции, стоит писать Request/Update, чтобы понимать что эта операция не просто получает или устанавливает значение для поля класса. Если мы хотим получить значение поля класса, которого может не быть при определенных обстоятельствах - лучше отразить это в методе и типе возвращаемого значения, наприме:
// Продолжительная операция, которая маскируется под быструю Get которая по идее просто получает поле класса
// Может вернуть nullptr, который обязательно разъименуют и выстрелят в ногу
auto GetNode(std::string name) -> Node*;
 
// Продолжительная операция, которая явно в API показывает, что может вернутся Node, или Error.
auto SearchNode(std::string name) -> Result<Node>
Наследование

Предпочитаем композицию наследованию. Но если делаем наследование - делаем его public.

Если нужно сделать private наследование - просто врубаем композицию и включаем объект как поле класса. Помечаем класс как final если не хотим чтобы его в будущем использовали как базовый класс.

Явно помечаем переопределенные методы как override (или final).

Не указываем virtual в дополнение к override/final : http://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines.html#c128-virtual-functions-should-specify-exactly-one-of-virtual-override-or-final

Можно пользоваться множественным наследованием от интерфейсов, но использовать множественное наследование не от чисто абстрактных классов - только в исключительных случаях.
Неявные преобразования

Стараемся минимизировать число неявных преобразований. Используем ключевое слово explicit для операторов и конструкторов с одним аргументом.

Исключения составляют только конструкторы копирования и перемещения, поскольку они не выполняют преобразование типов.

Однако, иногда неявные преобразования могут быть необходимы и уместны для типов, которые предназначены для взаимозаменяемости.

Тем не менее сначала пишем explicit, и только потом смотрим действительно ли нам нужны неявные преобразования для этого класса - скорее всего предстоит дискуссия на ревью.


Комментарии абсолютно необходимы для обеспечения читабельности нашего кода.

Но помните: хотя комментарии очень важны, лучший код — самодокументируемый.

Гораздо лучше давать осмысленные имена типам и переменным, чем использовать непонятные имена, которые потом придется объяснять в комментариях.
Стиль комментирования

Используем стиль комментирования doxygen https://www.doxygen.nl/manual/docblocks.html

Комментарии для документации ведутся на русском языке.

Комментарии, в рамках реализации ведутся на русском языке или английском языке.

Не используем trailing-комментарии, если хочется прокомментировать строчку - комментируем выше.
Комментарии к структурам и классам

Для не очевидного класса, или структуры пишем "шапку" - в чем назначение этого класса, что это такое, что он должен делать, и как должен использоваться:
/**
 * @brief Класс CommandBuffer представляет собой буффер для всех возможных команд,
 * которые мы можем отправить на испольнение в GPU.
 *
 * - тут можно раскрыть более подробно
 *
 * - а тут предоставить примеры
 *
 */
class CommandBuffer
{
    //...
};
Комментарии к методам и функциям

Почти каждое объявление функции должно иметь комментарии, предшествующие ему, которые описывают, что делает функция и как ее использовать. Эти комментарии можно опустить, только если функция проста и очевидна (например, простые методы доступа к очевидным свойствам класса).

Что следует упомянуть в комментариях к объявлению функции:

    Каковы входы и выходы функции. 
    Для функций-членов класса: запоминает ли объект аргументы ссылки или указателя за пределами продолжительности вызова метода.
    Для каждого аргумента-указателя указывается, может ли он быть нулевым и что произойдет, если это так.
    Что происходит для каждого выходного или входного/выходного аргумента с любым состоянием, в котором находится этот аргумент (например, добавляется ли состояние или перезаписывается?).
    Затратна ли функция по производительности? Необходимо подсвятить если это так.

Пример:
class CommandBuffer
{
    /**
     * @brief Заполняет буфер текстуры на GPU данными из CPU буффера.
     *
     * Метод ожидает, что размеры буффера на CPU совпадают с размером текстуры, и
     * обязанность клиента гарантировать это. В противном случае может произойти непридвиденное
     * завершенеи программы.
     *
     * @param tex - Объект текстуры на GPU. У него будет получена информация о размере.
     *
     * @param source_format - формат данных буффера на CPU (RGB8_UINT, RGBA8_UINT итд)
     *
     * @param bytes_data - Указатель на данные CPU-буффера. Может быть nullptr, в этом случае текстура зальется нулями
     */
    virtual void CopyTextureData( Texture const& tex, Format source_format, void* bytes_data ) = 0;
};
Комментарии к переменным и константам

В идеале, имя переменной должно быть достаточно информативным, чтобы дать хорошее представление о том, для чего она используется.

Но тем не менее в некоторых случаях требуются дополнительные комментарии.

Для переменных и констант необязательно использовать doxygen, но тем не менее можно

Пример:
int main() {
    /// \brief Это магическое число было сгенерировано особым магическим образом и влияет на абсолютно все в программе
    /// Не трогайте его
    int magicNumber = -34512;
     
    /// TODO: Выпилить по задаче RMSHT-1231
    int anotherMagicNumber = 123123;
}
Комментарии к глобальным переменным

Все глобальные переменные должны иметь комментарий, описывающий, что они собой представляют, для чего используются и (если неясно), почему они должны быть глобальными.

Пример:
/// Общее число тест кейсов, которое должно успешно завершиться чтобы UnitTest был успешно пройден
const int kNumTestCases = 6;
Комментарии TODO

Оставлять в комментариях TODO считаем нормальной практикой,

Например, если что-то было не сделано (не успевали к релизу), или найден баг/недоработка, но править по текущей задаче совсем не вариант.

Но оставлять комментарий TODO в коде без привязки к задаче - запрещено.

Пример:
// TODO: Если прилетит nullptr, то такого поворота судьбы редактор не переживет
// Будет исправлено в рамках VESDK-3252
Самодокументируемый код

Не комментируйте очевидное. В частности, не описывайте буквально то, что делает код, за исключением случаев, когда поведение не очевидно для читателя, хорошо понимающего C++.

Вместо этого предоставьте комментарии более высокого уровня, описывающие, почему код делает то, что он делает, а еще лучше сделайте код самодокументируемым.

Плохо, комментарий очевиден:
// Находим элемент в std::vector<>
if (std::find(v.begin(), v.end(), element) != v.end()) {
  Process(element);
}

Лучше:
// Обрабатываем "element" если он еще не был обработан.
if (std::find(v.begin(), v.end(), element) != v.end()) {
  Process(element);
}

Идеально - самодокументируемый код, которому не нужны комментарии (комментарий из примера выше тут был бы очевиден)
if (!IsAlreadyProcessed(element)) {
  Process(element);
}

Проектные оговорки (SC3)

Правила этого документа применяются к новому коду библиотеки SC3 со следующими уточнениями, принятыми для этого проекта:

1. Имена файлов — snake_case (например wavemark_encoder.h, bit_ring.cpp),
   несмотря на PascalCase в примерах выше.

2. snake_case-исключения — замороженный вендорский/интероп-слой, который
   не переименовывается: C-API (soundCodeEncoder_*, sc3_rvec_*), pffft,
   WASM-хосты (sc3_wasm_bindings, sc3_worklet_host). CamelCase — признак
   нашего слоя: по имени функции сразу видно, к какому миру она относится.

3. Докомментарии пишем на ВСЕ сущности и методы. Простым и понятным
   языком; сложные вещи стараемся объяснить просто. Лучше лишний
   абзац прояснения, чем загадочная формула без контекста.

4. TODO оставляем без привязки к задаче — просто TODO с пояснением.

5. Суффикс _t у старых типов (Vec_t, RVec_t и пр.) — легаси; новые типы
   зовутся без _t (Vec, RVec), старые имена живут как deprecated-алиасы
   до конца миграции.

6. Возврат функции пишем trailing return type: `auto Foo() -> Ret`.
   Сначала читаем, что функция делает (имя), потом что возвращает; имена
   функций выстраиваются в один столбец. Правило для всего нового кода и
   для любых сигнатур, которые мы и так трогаем; перевод существующих
   сигнатур — отдельными механическими коммитами (rename-only), никогда
   не в одном коммите с изменением поведения. Замороженный C-API
   (soundCodeEncoder.h) не переводится.

7. Итерацию по коллекции пишем range-based for. Если логическая длина
   меньше контейнера (например, каналы: массив [2], активны num_channels),
   итерируем подмножество через std::span(массив, count) — никаких
   индексных циклов с двойной границей `i < n && i < N`. Индексный for
   остаётся легален только для genuinely параллельных массивов (несколько
   коллекций, синхронно адресуемых одним индексом) и когда сам индекс —
   часть результата (счётчик).
